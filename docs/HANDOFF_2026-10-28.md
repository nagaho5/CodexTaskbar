# 1. 用户环境与硬约束

## 1.1 Windows / 任务栏

用户环境：

- Windows 10；
- Windows 任务栏固定在 **屏幕左侧，竖向**；
- 已长期使用开源项目 TrafficMonitor：
  - https://github.com/zhongyang219/TrafficMonitor
- TrafficMonitor 在左侧竖任务栏下方显示上传/下载、CPU、内存、显卡等信息；
- CodexTaskbar 应尽量显示在 **TrafficMonitor 上方**；
- 不能破坏 Windows 原任务栏按钮区域；
- 不能把已有任务栏区域挤掉、缩短或重排。

这条是硬约束。v0.1.2 曾经错误修改 `MSTaskSwWClass / MSTaskListWClass` 高度，导致几乎整个任务按钮区被挤没；v0.1.3 已永久改成“只叠加、不重排”，后续不要再恢复“给自己腾空间”的做法。

## 1.2 UI 偏好

用户偏好非常明确：

- 黑色背景；
- 白色文字；
- 与 Windows 黑色任务栏融合，不要突兀；
- 高信息密度；
- 字体不要太小；
- 字号支持直接输入数字调节；
- 尽可能紧凑；
- 文案越少越好；
- 常驻区域不要出现多余的 `5H`、`7D`、`C`、`K` 等标签；
- 完整含义放到鼠标悬浮信息里；
- 当前字体：Segoe UI Semibold；
- 当前字号允许 8–24 pt；
- 所有可显示字段都必须能在设置里独立勾选。

## 1.3 用户对复杂度的要求

项目起因之一就是用户已经对大型/复杂状态插件失去耐心。

硬原则：

- 轻量；
- 不做没必要的复杂后台系统；
- 不为了显示几个数字引入浏览器自动化、CDP、UIA 大型链路；
- 不建立本地统计数据库；
- 不高频扫描日志/Git；
- 不读聊天正文；
- 不修改 Codex；
- 不抢 thread owner；
- 不调用 `thread/resume` 去“占用/加载”会话；
- 尽量直接复用 Codex 已有本地官方数据；
- 失败时宁愿不显示，也不要显示“看起来精确但其实错误”的数字。

## 2.1 最初想找现成成熟项目

- 7 天额度；
- Windows Codex Desktop。

用户也看过/问过：

- Reddit / r/OpenaiCodex 帖子截图里的插件；
- 其他 stars 较多的 Codex 状态/配额工具。

但逐渐降低需求，最后明确：

> 不需要一堆复杂功能，只要能在任务栏紧凑显示 5h、7d，后来再加 Context / Cache / 当前代码改动即可。

## 2.2 之前折腾过 codex-statusbar

在 CodexTaskbar 之前，我们对：

- upstream：`dongyue-19/codex-statusbar`
- 用户 fork：`nagaho5/codex-statusbar`

做过完整源码审计、安全/性能硬化、Windows CI、自构建 Release。

这是很重要的背景，因为它直接解释了为什么 CodexTaskbar 不应该再走同一条复杂路线。

### codex-statusbar 的源码审计结论

当时确认：

- 没有生产网络请求；
- 没有 telemetry；
- 没有第三方 NuGet PackageReference；
- 没有 DLL/process injection；
- `OpenProcess` 仅使用 `PROCESS_QUERY_LIMITED_INFORMATION`；
- `state_5.sqlite` 只读打开；
- rollout/session JSONL 只读打开；
- named pipe 是 `\\.\pipe\codex-ipc`；
- README 写“read-only IPC”并不完全精确：实际连接是 `PipeDirection.InOut`，因为要发送 initialize，再接收广播；
- 没有发现修改 thread/chat/settings 的命令；
- config.toml 原实现为了只读 theme 却会整文件读取；
- debug.log 原实现无上限；
- 开机启动只写 HKCU Run，不需要管理员；
- self-contained .NET 单文件会在 `%TEMP%\.net` 做少量原生库解压，并非绝对零磁盘写入。

### 当时发现的主要性能问题

原项目 `RolloutReader.TryUpdate()` 在 ACTIVE 状态约每 350ms：

- reopen rollout；
- 为判断文件替换反复读最多 64KB 文件头。

逻辑读取量大约：

- 64KB / 0.35s；
- ≈183KB/s；
- ≈640MB/h；
- ≈15GB/day（连续运行的逻辑读取量）。

这主要是文件缓存逻辑读，不等价于 SSD NAND 写入/TBW，但属于不必要活动。

### 我们对 codex-statusbar 做过的 hardening

最终 fork 主线做过：

1. rollout 文件 ID 检测：
   - Windows `GetFileInformationByHandle`
   - VolumeSerialNumber + FileIndexHigh + FileIndexLow
   - 正常情况下避免每 350ms 重读 64KB 头；
   - 文件 ID 不可用时才 fallback 原逻辑。

2. config.toml：
   - `File.ReadAllLines` → `File.ReadLines`
   - 10s TTL + LastWriteUtc/Length stamp
   - 未变化时不重读内容。

3. debug.log：
   - 仍保留 `--debug`
   - 默认关闭；
   - 单日志约 5MB 上限；
   - 一个 `debug.log.1` 备份；
   - 防止无限增长。

4. restart 参数：
   - 改用 `ProcessStartInfo.ArgumentList`
   - 避免拼接字符串参数边界问题。

5. settings：
   - 临时文件 + `File.Replace` / `File.Move`
   - 原子保存。

6. SelfTest：
   - 加文件替换检测；
   - debug cap；
   - atomic settings；
   - theme cache；
   - 最后 305 checks / 0 failures。

7. GitHub Actions：
   - Windows CI；
   - pinned actions；
   - PR build；
   - workflow_dispatch Release；
   - 正式 self-build Release `self-build-4-1`。

### 为什么最终放弃继续修 codex-statusbar

真机使用时仍遇到很多问题：

- TPS 经常为 `-- tok/s`；
- 切换会话后显示旧会话数据；
- 当前会话识别不稳定；
- “锁定当前会话”也不能解决；
- 详情面板闪一下消失；
- 详细项为 0；
- 状态 fallback 造成：
  - tray tooltip 能显示 state DB total；
  - 主条却显示 `0 tok / Cache --`；
- 原项目 collapsed total 使用 `Input + Output` 而非 `snapshot.TotalTokens`，存在明确显示 bug；
- 其 current-thread / rollout 绑定设计过于复杂；
- 用户认为实时 TPS 本身也未必准确，投入继续修复没有意义。

用户最终明确：

> 这个项目没必要再修下去了，问题太多，而且最想看的实时速度也未必准确。

因此 CodexTaskbar 的核心设计方向是：

> **抛弃 TPS，抛弃复杂会话状态条，重新做一个极简、任务栏原生感、只展示真正有意义数据的小工具。**

# 4. 架构选择

## 4.1 技术栈

最终选择：

- 原生 Win32 C++；
- C++20；
- CMake；
- MSVC；
- native Windows x64 EXE；
- 不依赖 .NET Runtime；
- 不依赖 Qt/Electron；
- EXE 一直保持在几十 KB 到约 160KB 级别。

当前主要源码：

- `src/main.cpp`
  - Win32 窗口；
  - 任务栏嵌入/定位；
  - 绘制；
  - 设置；
  - 托盘；
  - hover tooltip；
  - Codex Desktop 前台窗口检测。
- `src/AppServerClient.cpp/.h`
  - 额度读取；
  - `account/rateLimits/read`。
- `src/DesktopThreadMonitor.cpp/.h`
  - Codex Desktop 本地 IPC follower；
  - Thread state；
  - Context；
  - Cache；
  - turn diff。
- `src/SimpleJson.cpp/.h`
  - 自带轻量 JSON parser；
  - JSON patch reducer。
- `src/CodexTaskbar.manifest`
- `src/CodexTaskbar.rc`

## 4.2 5h / 7d 配额来源

配额来自官方 Codex app-server：

- `account/rateLimits/read`

第一版为了读取额度，在 Codex 开着时启动隐藏 `codex app-server` 子进程。

用户关心“手动立即刷新有没有意义”时，我们的结论是：

- 自动刷新即可；
- 目标是和 Codex 自己看到的额度一致；
- 不需要高频刷新；
- 当前自动刷新约 60 秒；
- “重新连接”更多是故障恢复，不是日常必须点。

## 4.3 Context / Cache / Diff 来源

后续加 Thread 指标后，使用：

- Codex Desktop 本地 IPC：
  - `\\.\pipe\codex-ipc`

设计原则：

- follower 只读；
- 不 `resume`；
- 不发送 prompt；
- 不抢 owner；
- 不修改 Codex；
- 不读取/保存聊天正文；
- 不扫描 Git；
- 不建立数据库。

# 9. Thread 绑定设计

用户明确问过两档方案。

## 9.1 第一档：手动绑定 Thread ID

这是默认、推荐、优先保证稳定的模式。

用户操作：

- 打开 Codex 状态窗口；
- 找：
  - `会话/聊天：xxxxxxxx-xxxx-....`
- 完整复制 Thread ID；
- 粘贴到 CodexTaskbar 设置。

用户曾截图确认过真实 Thread ID，格式正确。

注意：

> 本文不在公开仓库记录用户实际完整 Thread ID，避免公开真实会话标识。不要把某个测试 Thread ID hardcode 到源码。

## 9.2 第二档：自动跟随活动任务

用户要求：

- 可以做；
- 但必须是设置中的可选项；
- 如果不稳定，用户会切回手动绑定；
- 不能为了自动模式破坏手动模式可靠性。

当前实现：

- 观察其他 Codex Desktop client 的 `thread-stream-following-changed`；
- 自动跟随最新活动 Thread；
- 最多保留有限订阅；
- manual thread 不被自动淘汰；
- 有 active turn 时优先选活动 Thread。

这仍然属于实验功能，不应把它宣传为比手动模式更可靠。

# 18. 当前 follower IPC 生命周期

`DesktopThreadMonitor` 当前设计：

- 连接 `\\.\pipe\codex-ipc`；
- initialize client type：
  - `codex-taskbar`
- 通过 `thread-stream-following-changed` follow thread；
- 处理：
  - snapshot；
  - patches；
  - JSON patch；
- 支持：
  - `client-discovery-request`
  - `thread-stream-following-status-requested`
  - `client-status-changed`
  - `ipc-connection-reset`
- owner 重连时重新 announce follow；
- owner 断开时清掉对应 document state；
- pipe/reset 后重新 follow；
- manual / auto 切换会重新配置。

安全原则：

- 不发业务 prompt；
- 不 resume；
- 不接管 Thread；
- follower 为观察者。

- `@pierre/diffs` summary 规则。

目标是让：

- exact same `turn.diff`
- 经过我们的 parser
- 得到和 Codex UI `getDiffSummary()` 一样的 files/additions/deletions。

### 如果第三行完全不出现

检查 canonical state 里最新 turn 是否真的包含 `diff`。

需要做观察型 debug：

- Thread ID；
- turn ID；
- status；
- 是否找到 `turnHistory.history.islands`；
- latest entry key；
- entity 是否存在；
- diff type（string/object/null）；
- unifiedDiff 字段是否存在；

不要记录聊天文本内容。

# 30. 最后一个对话节点（非常重要）

用户在 v0.2.2 真机测试后的最后补充是：

> “补充：任务中也比这个少，我安装的时候代码以后+1300了，这个显示958，到最后完成时还是这样”

含义：

- Codex 自己任务中已经累计新增约 +1300；
- CodexTaskbar 仍显示 +958；
- 完成后 Codex 最终为 +1461 / -327；
- CodexTaskbar 仍停留 +958（删除也明显不足）；
- 因此旧实现不是延迟，而是数据源错误。

随后上一位模型完成并发布了 v0.2.3，并说明：

- hover 按 TrafficMonitor 实现思路重做；
- 250ms 显式 hover；
- canonical latest turn；
- exact `turn.diff`；
- 不再使用 fileChange；
- 如果拿不到 exact diff 就不显示第三行；
- 同一 turn patch gap 保留 last exact diff；
- 新 turn 才清旧值；
- CI 0 warnings / 0 errors。

就在这个回复之后对话达到长度上限，用户无法继续回复，于是回退到上一节点并要求创建本交接。

因此：

> **v0.2.3 是当前待真机验证的版本，不是已由用户确认完全正确的版本。**
