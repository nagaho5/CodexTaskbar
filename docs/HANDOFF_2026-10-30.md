# 1. 用户环境、体验目标和硬约束

## 1.1 操作系统 / 任务栏环境

用户主要环境：

- Windows 10；
- Windows 任务栏固定在屏幕左侧，竖向；
- 长期使用 TrafficMonitor；
- TrafficMonitor 位于左侧任务栏下方；
- CodexTaskbar 应尽量位于 TrafficMonitor 上方；
- 后来增加主屏 / 副屏任务栏选择；
- 用户希望工具可以长期后台常驻，尽量轻量。

硬约束：

- 不得缩短、重排或挤占 Explorer 原任务按钮区域；
- CodexTaskbar 必须是 overlay/附加式，而不是“给自己腾空间”；
- 不要为了一个小工具引入大型 runtime 或复杂依赖；
- 不要频繁读磁盘；
- 不要建立数据库；
- 不要扫描 Git 来统计 diff；
- 不要读取聊天正文；
- 不要修改 Codex Desktop；
- 不要抢 thread owner；
- 不要通过 thread/resume 加载/接管会话。

## 1.2 UI 偏好

用户对 UI 的要求非常稳定：

- 黑色背景；
- 白色普通文字；
- 高信息密度；
- 少留白；
- 字体偏大但任务栏很窄，因此需要紧凑；
- 能省一个字符就不要浪费；
- 常驻 taskbar 区域尽量只显示数字，不要 5H/7D/C/K 等标签；
- 完整含义放 hover；
- 新增/删除行用绿/红；
- 运行中可以用自定义工作颜色；
- 设置项多时，宁可把设置窗口做大，也不要硬挤在 500px 宽度里。

## 1.3 对稳定性的要求

非常重要：

- 用户长期日用时优先“稳定”而不是“自动化”；
- 自动跟随 Thread 如果不稳，可以彻底不用；
- 手动绑定 Thread 是当前推荐/默认路径；
- 不允许为了自动模式破坏手动模式；
- 用户明确表示自动跟随活动任务“现阶段弃用”，代码可以留着以后研究；
- 不要为了修实验自动模式增加常驻硬盘读取或功耗。

## 1.4 真机 PASS 规则

必须严格区分：

- GitHub Actions Build PASS；
- Release workflow PASS；
- 用户真机体验 PASS。

用户多次要求：

> 没有实际在他的 Windows 10 上验证过，就不要说功能已经“PASS”。

  - TPS 经常 --；
  - 切会话显示旧数据；
  - current thread 识别不稳；
  - 详情 popup 闪退；
  - 状态 fallback 不一致。

> 放弃复杂状态条，自己写一个极简 Win32 小工具，只显示真正可靠、有意义的数据。

因此 CodexTaskbar 的设计哲学从一开始就是：

- native；
- 小；
- 直接；
- 低 I/O；
- 数据不可靠时宁可显示 -- / 暂无；
- 不要伪精确。

# 4. 任务栏挂载与 Explorer 相关结论

## 4.1 当前挂载方式

CodexTaskbar 会把自己的 widget 作为 Explorer taskbar 内部窗口树中的 child，目标主要是：

- 主屏：Shell_TrayWnd
- 副屏：Shell_SecondaryTrayWnd
- 再查 ReBarWindow32 / WorkerW

这属于跨进程 taskbar child/window parenting。

## 4.2 绝对不要再做的事情

早期某版本曾错误修改：

- MSTaskSwWClass
- MSTaskListWClass

高度，结果把任务按钮区域挤坏。

之后已经永久改成：

> 只 overlay，不重排 Explorer task list。

后续绝对不要恢复“为了 CodexTaskbar 腾空间而 resize Windows task-list”的设计。

## 4.3 Explorer 重启问题：未最终定性

用户观察到更新/启动某些版本时：

- Windows Explorer 似乎会重启；
- taskbar/桌面可能刷新。

当前源码中没有：

- taskkill explorer.exe
- TerminateProcess(explorer)
- RestartExplorer
- 任何主动杀 Explorer 的代码。

v0.3.8 updater 也只会停止 CodexTaskbar，不会主动停止 Explorer。

因此如果再次出现 Explorer 真重启：

优先让用户确认：

- 事件查看器
  - Windows 日志
  - 应用程序
  - Application Error / explorer.exe
  - Event ID 1000
- 或可靠性监视器

如果能确认 explorer.exe 真 crash，再考虑是否和跨进程 child-parent / DPI / taskbar 内部窗口交互有关。

不要直接宣称“肯定是 CodexTaskbar”或“肯定不是 CodexTaskbar”。

如果长期证实 taskbar child 架构导致 Explorer 不稳，可以考虑未来大改成独立 top-level overlay，但这会涉及：

- z-order
- 全屏窗口
- taskbar auto-hide
- DPI
- 点击
- Explorer 重建

不要轻易重构。

早期错误：

- 用 last request cache ratio，容易长期 100%。

- cachedInputTokens / inputTokens

用户要的是：

> Codex Desktop 自己当前 Turn 显示的最终代码改动统计。

不是：

- Git working tree；
- 累加 patch；
- 任意 fileChange 中间过程累计。

最终逻辑：

- exact turn diff 最优先；
- exact diff 不存在时用 current canonical Turn 的 completed fileChange fallback；
- fallback 只看当前 Turn；
- exact 出现后覆盖 fallback。

用户对 v0.2.6 的真机反馈：

所以 diff 不要重新大改数据源，除非用户再次给出明确不一致证据。

# 7. 自动跟随活动任务：v0.3.0～v0.3.2 的失败/诊断史

这是本项目最容易被下一位模型误判、重复折腾的一段。

## 7.1 用户实际反馈

“自动跟随活动任务（实验）”经常：

- A → B 成功；
- B → A 不再切回来；
- 在多个对话 A/B/C/D 来回切换时“时灵时不灵”；
- 找不到稳定规律。

用户最后决定：

> 自动功能目前问题很大，先用手动；
> 自动模式代码可以留着，以后再研究；
> 现阶段尽量不要为它增加硬盘读写和功耗。

## 7.2 v0.2.9 自动跟随旧逻辑的核心 bug

旧字段：

- states_
- followed_
- autoSelectedThread_
- latestRouteThread_

旧选择逻辑：

1. sticky autoSelectedThread_
2. newest active Turn
3. latest route

旧问题：

- latestRouteThread_ 不是最高优先；
- activeTurn 会把显示粘在旧 Thread；
- 如果切回一个已经在 followed_ 中的 Thread：
  - FollowThread(thread,true) 会直接 return；
  - 不重新 announce；
  - owner/snapshot 不刷新；
- following=false 被完全忽略；
- late patch/snapshot 可能继续影响选择。

典型 A → B → A：

1. B route 到来；
2. B active，autoSelectedThread_=B；
3. 切回 A；
4. A 已在 followed_，FollowThread(A,true) no-op；
5. autoSelectedThread_ 仍 B；
6. UI 卡在 B。

## 7.3 v0.3.0 / PR #14

PR #14：

“Stabilize automatic thread following in v0.3.0”

主要改成：

- 删除 sticky autoSelectedThread_；
- Desktop UI route highest priority；
- latest untargeted thread-stream-following-changed 作为 UI route；
- A → B → C → A 应立即切 A；
- 已 follow 的 Thread 再进入时仍重新 SendFollowFrame(true)；
- late old-thread updates 只能更新 cache，不能抢 display；
- 处理 following=false；
- fresh snapshot 未到时：
  - 显示 routed thread pending/empty；
  - 不显示另一条 active thread；
- active-turn heuristic 只在 route 真不存在时 fallback；
- manual mode 不变。

这是正确的状态机方向，但真机仍没有达到用户想要的稳定度。

## 7.4 用户要求参考开源项目 / Codex 源码

用户问过：

> 要不要看看类似开源项目如何处理？Codex 源码也应该是公开的。

当时参考过：

- anywherelabs/Agents-Anywhere

- OpenAI Codex 相关 IPC 语义

但这些仍不能保证 Codex Desktop Windows UI 的“当前页面”在所有情况下能被这个信号唯一、稳定地识别。

## 7.7 最终自动模式结论

# 17. 生成速度当前算法与不要再踩的坑

## 17.1 数据

使用累计 outputTokens。

不是：

- totalTokens
- inputTokens

原因：

total 包含大块 input/cache，不能代表模型吐字速度。

## 17.2 当前实时 sample

概念：

- delta output tokens / delta time

但要处理：

- IPC burst；
- tiny interval；
- tool/network pause。

## 17.3 tiny interval

v0.3.8 的错误：

- <250ms reject
- 又更新 baseline
- 导致永久暂无

v0.3.9 正确：

- <250ms：
  - keep baseline
  - accumulate

## 17.4 long gap

long gap 不计速度。

threshold：

- 初期约 5 秒；
- 有样本后：
  - max(3 秒, median interval x 4)

## 17.5 recent average

窗口：

- 最近最多 8 个 accepted samples

显示平均条件：

- 至少 5 个

算法：

- sort
- 去最高
- 去最低
- mean remaining

不要再恢复：

- whole-Turn sample sum / sample count

因为用户真机已经出现 4489.1 token/s 这种无意义值。

## 17.6 taskbar speed mode

设置：

- 实时速度
- 最近平均

average mode：

- <5 accepted samples：
  - fallback current speed
- >=5：
  - robust recent average

# 18. 5h 消耗速度当前算法

这是“估算”，不是高精度 billing meter。

## 18.1 为什么天然粗

quota 剩余百分比：

- 整数粒度；
- 正常约 60 秒刷新。

所以短任务：

- 可能很久 0.000；
- 然后突然跳。

这是数据粒度问题，不要为了追求平滑擅自高频 quota poll。

## 18.2 observation-aligned baseline

baseline 必须是一对：

- remainingPercent
- quotaSnapshotTimestamp

当前 rate：

- consumed = baselineRemaining - currentRemaining
- elapsed = currentQuotaSampleTime - baselineQuotaSampleTime

rate：

- consumed / elapsedMinutes

## 18.3 排除 task 前连接

只有任务已经进入 first real work 后，才允许建立 baseline。

## 18.4 程序中途启动

如果任务已经运行 10 分钟，此时才启动 CodexTaskbar：

- 不使用历史 firstWork time 做 denominator；
- 第一份程序真正观察到的 post-work quota snapshot = time zero。

这条是用户明确补充的硬要求。

## 18.5 任务完成

保留最后有效 rate：

- hover 继续显示上一轮最终值。

下一轮：

- 网络/初始化等待阶段可以继续显示旧 final；
- 真正建立新 baseline 时再清。

# 20. 性能 / I/O 当前结论

## 20.1 manual mode

## 20.2 named pipe

Desktop IPC：

- 不是硬盘读；
- ReadFile 读的是 named pipe。

v0.3.5：

- idle poll 从约 10ms loop 改成 interruptible 500ms wait；
- 空闲最多约 2 wakeups/s；

## 20.3 hover

- 不再永久 200ms polling；
- mouse event driven；

## 20.4 taskbar position

v0.3.5 后：

- 不再每秒 PositionWidget；
- meaningful change 立即；
- 10 秒 fallback。

v0.3.8：

- startup/display change 短时 200ms readiness；
- 最多 5 秒；
- 不是常驻 polling。

## 20.5 saved threads

保存多个 Thread：

- 只是 Registry strings；
- runtime 只 follow 当前一个；
- 保存 20 个也不等于 follow 20 个。

## 20.6 speed average/history

只有几个内存数字。

- IPC query
- disk read
- quota request
- timer

## 20.7 future

- overlapped/event-driven named pipe

目标：

- idle 0 wakeup。
